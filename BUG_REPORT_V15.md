# V15 Bug Report

Date: 2026-07-28

## Scope Tested

- Account bootstrap and authenticated table creation.
- Admin/Warden table directory access.
- Table lock and locked-player join handling.
- Warden transfer between seated users.
- Player removal from a table.
- Table archive and reopen.
- Table audit feed entries for moderation actions.
- Admin and Player inline script parsing.

## Bugs Found and Fixed

### Account client identity mismatch

Authenticated account users could still report the older browser client ID in some sync status and self-update checks. This could make player-owned request tracking and local self-sync detection behave incorrectly after login.

Fix: `VGSync` now uses the effective account-backed client ID for status, pull/apply self checks, and Warden snapshot pushes.

### Locked table had no player-facing waiting state

When a table rejected a join because it was locked, the Player page only surfaced the generic join failure path.

Fix: locked joins now return a `423` response with `locked: true`, and the Player page renders a compact waiting-room message.

### Invite link path regression risk

The live app serves the player page at `/player/player.html`, not `/player/`.

Fix: invite links generated by Admin point to `/player/player.html?invite=CODE`.

## Verification Result

Passed locally:

- Guest/late assigned player receives locked-table denial.
- Assigned Warden/Admin can manage table operations.
- Warden transfer updates the seated player role.
- Removed players disappear from the table payload.
- Archive and reopen update table state correctly.
- Audit includes lock, kick, and Warden transfer events.

## Watch Items

- The control room intentionally requires an authenticated Owner, Admin, or assigned Warden account.
- Table rename uses a browser prompt in V15; a dedicated inline edit control would be cleaner later.
- Archived tables remain visible in the directory for recovery and audit visibility.
